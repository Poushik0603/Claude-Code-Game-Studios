# Player Identity/Session

> **Status**: In Design
> **Author**: user + agents
> **Last Updated**: 2026-09-29
> **Last Verified**: 2026-09-29
> **Implements Pillar**: Pillar 1 (Zero Friction to the Table), Pillar 3 (Never Lose Your Seat)

## Summary

Player Identity/Session defines what "being a player" means before any room or game exists — a session token, generated by the server and held in the client's `sessionStorage`, that uniquely identifies one browser tab across reconnects. It is the foundation Pillar 1's "no accounts, just type a name" promise is built on, and the exact mechanism Pillar 3's "never lose your seat" depends on: the token is what lets a refreshed tab prove "I am the same player who was just here," while a brand-new tab — with no token — is unambiguously a different player, even from the same person on the same device.

> **Quick reference** — Layer: `Foundation` · Priority: `MVP` · Key deps: `None`

## Overview

This system establishes a lightweight, account-free session identity for each connected browser tab. On first connection, the server generates a random, unguessable session token and sends it to the client, which stores it in `sessionStorage` — a browser storage mechanism that is scoped per-tab and cleared when the tab closes, but survives page refreshes within that tab. This gives the game exactly the identity model the brief requires: two tabs open by the same person are two distinct sessions (no shared `sessionStorage`), while refreshing or briefly losing connection in one tab preserves that tab's identity (the token survives). A `Player` in this system's model is the pairing of a chosen `displayName` (freely reused — "Alex" and "Alex" are not merged or blocked) with a server-issued `sessionId`; the two together, plus a room membership established via `JOIN_ROOM`, are what the Reconnection & Session Identity system later uses to restore a rejoining player's exact seat and hand. This system defines *only* the identity primitive — it does not implement room membership, seat assignment, or reconnection logic itself; those are separate systems that consume this one's `sessionId` concept.

## Player Fantasy

This is the moment Pillar 1 lives or dies: the instant between typing a name and being "in." There's no visible mechanism here — no "creating your session," no spinner, no account screen — the player just types a name and the game responds as if they were already expected. The feeling this system enables is closer to walking into a room where everyone already knows your seat is there, not "signing up" for anything. Its second, quieter fantasy shows up later: when a connection drops and the player panics for a second — *did I lose my hand?* — and then it's just... still there. The system's success is measured by the player never consciously noticing it worked; the failure mode is the player noticing it *didn't*.

## Detailed Design

### Core Rules

1. A `Session` is created the moment a client's Socket.IO connection is established — before any name is entered or room is joined. Its identity is `{ sessionId: string }`, where `sessionId` is a server-generated `crypto.randomUUID()`.
2. The server sends the `sessionId` to the client immediately on connection via a new broadcast type, `SESSION_ESTABLISHED` — an additive extension to the WebSocket Message Protocol's message catalog, consistent with that GDD's own Open Question anticipating additive extension.
3. The client stores `sessionId` in `sessionStorage` under a fixed key. On every subsequent connection attempt (page refresh, brief network drop) within the same tab, the client reads the stored `sessionId` and sends it back to the server as part of the initial handshake, instead of receiving a new one.
4. If the server receives a `sessionId` it recognizes (i.e., a session record still exists for it), the client's Socket.IO connection is re-associated with that existing session — this is what makes "refresh doesn't lose your seat" possible at the identity layer. If the server does not recognize the `sessionId` (expired, server restarted, or genuinely new), it issues a fresh one — the client transparently gets a new session with no error shown to the player.
5. A `Player` is formed once a session acquires a `displayName`, which happens via the `JOIN_ROOM` intent (`{ roomCode, displayName }`, per the WebSocket Message Protocol GDD). Before that point, a session has no display name and is not yet a "player" in any room.
6. `displayName` is **not unique** — the system never blocks, merges, or disambiguates two sessions choosing the same name (explicit brief requirement). Any collision handling (e.g., showing "Alex (2)" in a room's UI) is a presentation concern for Room/Lobby / Game Table UI, not an identity-layer concern.
7. A session's `sessionId` is never exposed to *other* players' clients — only the owning client knows its own `sessionId`. Other clients identify players by `displayName` + a server-assigned, non-secret `playerId` (distinct from `sessionId`) used for redaction-safe references in broadcasts (e.g. `CATCH_UNO`'s `targetPlayerId`). This separation exists so a session token (which can reconnect on your behalf) is never accidentally leaked to another client, while a `playerId` (safe to be public within a room) is what other systems reference.
8. This system does not implement room membership, seat numbers, or turn order — those are Room/Lobby and Rules Engine concerns that reference a session's `playerId`.
9. `sessionId` must never appear in server logs, error responses, telemetry, or any output that could reach a client other than its owner or a third-party service — logging/observability tooling logs `playerId` (safe, public) instead when a player reference is needed. This extends the sessionId/playerId separation in Core Rule 7 to non-broadcast surfaces (logs, crash reports, analytics), not just player-to-player messages.

### States and Transitions

| State | Entry Condition | Exit Condition | Behavior |
|-------|----------------|----------------|----------|
| `connecting` | Socket.IO connection initiated, no `sessionId` yet exchanged | `SESSION_ESTABLISHED` sent/received | Transient — client has no identity yet |
| `identified` | `SESSION_ESTABLISHED` received (new or resumed) | `JOIN_ROOM` succeeds | Session exists, no `displayName`/`playerId`/room yet |
| `active_player` | `JOIN_ROOM` succeeds | Socket disconnects | Session has `displayName`, `playerId`, and room membership |
| `disconnected` | Socket disconnects while `active_player` | Reconnect with matching `sessionId` (→ `active_player`) or session record is evicted (→ terminal) | Session record persists server-side; player shows as disconnected to others (Reconnection & Session Identity GDD owns the exact grace-period/eviction policy) |

### Interactions with Other Systems

| System | Data In | Data Out | Notes |
|---|---|---|---|
| WebSocket Message Protocol | — | New broadcast `SESSION_ESTABLISHED { sessionId }`; consumes `JOIN_ROOM`'s `displayName` | Additive extension to that GDD's catalog, per its own Open Questions note |
| Room/Lobby | Consumes `playerId` + `displayName` to build lobby membership | — | Room/Lobby is where `playerId` becomes "a seat in a room" |
| Reconnection & Session Identity | Consumes the `sessionId` resume mechanism (Core Rule 4) as its foundation | — | That GDD will define the exact grace period, eviction timing, and mid-game state restoration; this GDD only defines that resumption is *possible* |
| Rules Engine — Normal UNO (and future modes) | Consumes `playerId` to attribute turns/hands | — | Never sees `sessionId` — only the safe, public `playerId` |

## Formulas

> Note: orphaned-session cleanup/eviction timing is intentionally out of scope here — owned by the not-yet-written Reconnection & Session Identity GDD (see States and Transitions above).

### Session ID Collision Probability

The Session ID Collision Probability formula is defined as:

`P_collision ≈ (n^2) / (2 * 2^122)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| Number of concurrently live sessions | n | int | 0–10^6 (generous ceiling for this game's scale) | Count of active `sessionId`s held in server memory at once, across all rooms |
| Collision probability | P_collision | float | 0–1 | Probability that two live sessions share a `sessionId` (birthday-bound approximation on UUIDv4's 122 random bits) |

**Expected output range**: Unbounded input, output clamped to [0,1] by construction of the approximation; in practice always ≈0 at this game's scale.
**Example**: At n = 10,000 concurrent sessions (far beyond any realistic single-server UNO deployment of 2–12 players/room), P_collision ≈ (10,000²) / (2 × 5.3×10^36) ≈ 9.4×10^-30 — safe to treat as zero. This is why Core Rule 1 does not require a server-side uniqueness check against existing session records when generating a new `sessionId`.

## Edge Cases

| Scenario | Expected Behavior | Rationale |
|----------|------------------|-----------|
| Client's `sessionStorage` is cleared or unavailable (private browsing edge cases, browser settings) | Client has no stored `sessionId` on next load; server issues a brand-new session, indistinguishable from a genuinely new player | Graceful degradation — worst case is losing "remember me across refresh" for that browser, not a crash or error shown to the player |
| Client sends a `sessionId` on reconnect that the server has never seen (forged, tampered, or from a session already evicted) | Server treats it identically to "no `sessionId` provided" — issues a fresh session, does not error or reveal whether the submitted ID was ever valid | Prevents an attacker from probing which session IDs are/were valid (information leak); fails safe by falling back to "new session," never by granting access to someone else's session |
| Two different browser tabs (same person, same browser) both connect and store `sessionId`s independently | Each gets its own session — this is the explicit intended behavior, not an edge case to "fix" | Per brief: two tabs = two players, by design |
| The server restarts (all in-memory session records lost) while clients hold now-unrecognized `sessionId`s | Every client's next reconnect attempt falls into the "server doesn't recognize this sessionId" path (Core Rule 4) and receives a fresh session | Given this project's explicit no-persistence design (Anti-Pillars: no game history, no save data), losing in-progress games on a server restart is an accepted tradeoff, not a bug this system must prevent |
| A client attempts to call `JOIN_ROOM` (acquire a `displayName`) more than once on the same session (e.g. re-entering a name, or trying to join a second room while already in one) | Out of scope for this GDD — Room/Lobby owns whether/how a session can hold membership in more than one room or change its `displayName` mid-session; this system only guarantees the `sessionId`↔`displayName` pairing mechanism exists | Keeps this system's boundary strictly to identity, not room-membership rules |

## Tuning Knobs

| Parameter | Current Value | Safe Range | Effect of Increase | Effect of Decrease |
|-----------|--------------|------------|-------------------|-------------------|
| `sessionId` generation method | `crypto.randomUUID()` (UUIDv4, 122 random bits) | Must remain cryptographically random | N/A | A weaker/shorter random source would raise collision probability and make session IDs guessable — not a tunable tradeoff, a correctness requirement (see Formulas) |
| `sessionStorage` key name | Implementation-chosen fixed string | Any string, must not collide with other client-side storage keys | N/A | N/A — purely an implementation naming choice, no gameplay effect |

## Acceptance Criteria

### Core Rule 1 — Session creation on connect
- [ ] GIVEN a client with no prior `sessionId`, WHEN a Socket.IO connection is established, THEN the server creates a session record before any `JOIN_ROOM` or name-entry message is processed.
- [ ] GIVEN a new session is created, WHEN its `sessionId` is inspected, THEN it is a `crypto.randomUUID()`-format value (RFC 4122 v4, 36-char hyphenated string).
- [ ] GIVEN two separate connections with no submitted `sessionId`, WHEN each is assigned a session, THEN the two `sessionId` values are different.

### Core Rule 2 — SESSION_ESTABLISHED broadcast
- [ ] GIVEN a client connects for the first time, WHEN the server finishes session creation, THEN the server sends a `SESSION_ESTABLISHED` message containing `{ sessionId }` to that client only (not broadcast to other clients).
- [ ] GIVEN a client reconnects with a recognized `sessionId`, WHEN the server re-associates the connection, THEN the server still sends `SESSION_ESTABLISHED` with that same `sessionId` back to the client.
- [ ] GIVEN the `SESSION_ESTABLISHED` message is sent, WHEN its payload is inspected, THEN it contains no fields beyond `sessionId` (no `displayName`, no `playerId`, no other session's data).

### Core Rule 3 — Client storage and resend on reconnect
- [ ] GIVEN a client receives `SESSION_ESTABLISHED`, WHEN the client processes it, THEN the `sessionId` is written to `sessionStorage` under the fixed key.
- [ ] GIVEN a tab with a `sessionId` already in `sessionStorage`, WHEN the page is refreshed, THEN the client reads the stored `sessionId` and sends it in the initial handshake instead of requesting a new session.
- [ ] GIVEN a tab experiences a brief network drop and Socket.IO auto-reconnects, WHEN the reconnect handshake fires, THEN the client sends the stored `sessionId` (not omitted, not regenerated).

### Core Rule 4 — Server recognition and re-association / fresh issuance
- [ ] GIVEN the server holds an active session record matching a submitted `sessionId`, WHEN a client reconnects with that `sessionId`, THEN the server re-associates the new Socket.IO connection with the existing session record (same `sessionId`, same `playerId`/`displayName`/room membership if present).
- [ ] GIVEN the server does NOT hold a record for a submitted `sessionId` (expired, evicted, or never issued), WHEN a client connects with that `sessionId`, THEN the server issues a brand-new `sessionId` via `SESSION_ESTABLISHED` and does not return an error to the client.
- [ ] GIVEN a fresh `sessionId` is issued after a rejection, WHEN the client UI is observed, THEN no error message, toast, or visual indication of "invalid session" is shown to the player.

### Core Rule 5 — Player formed via JOIN_ROOM
- [ ] GIVEN a session with no `displayName`, WHEN `JOIN_ROOM { roomCode, displayName }` is sent and succeeds, THEN the session is now associated with that `displayName` and is considered a `Player`.
- [ ] GIVEN a session has not yet sent a successful `JOIN_ROOM`, WHEN the session's state is inspected, THEN it has no `displayName` and is not treated as a player by any room-facing system.

### Core Rule 6 — displayName is not unique
- [ ] GIVEN a room already contains a player with `displayName` "Alex", WHEN a second session sends `JOIN_ROOM` with `displayName` "Alex" for the same room, THEN the join succeeds without error, merge, or forced renaming at the identity layer.
- [ ] GIVEN two sessions share the same `displayName` in the same room, WHEN each session's `playerId` is inspected, THEN the two `playerId` values are distinct (disambiguation is by `playerId`, never by mutating `displayName`).

### Core Rule 7 — sessionId (private) vs playerId (public) separation
- [ ] GIVEN Player A is in a room with Player B, WHEN any broadcast message that references Player A is sent to Player B's client (e.g., `CATCH_UNO`'s `targetPlayerId`), THEN the payload contains Player A's `playerId` and `displayName` only — Player A's `sessionId` is absent from the message entirely.
- [ ] GIVEN a client inspects any message it has received from the server (of any message type) that is not its own `SESSION_ESTABLISHED`, WHEN the message payload is searched, THEN it contains no `sessionId` field for any player other than (implicitly) the receiving client's own session.
- [ ] GIVEN a fresh connection with a submitted `sessionId` that does not match any server record, WHEN the server responds, THEN the response reveals no information about whether that `sessionId` was ever previously valid/issued (identical response to "never seen before").

### Core Rule 8 — Scope boundary (no room/seat/turn logic here)
- [ ] GIVEN this system's implementation, WHEN searched for seat-number, turn-order, or room-membership storage logic, THEN none exists within the identity/session module — only `sessionId`, `playerId`, and `displayName` pairing.
- [ ] GIVEN a `playerId` is issued, WHEN a downstream system (Room/Lobby, Rules Engine) needs seat or turn data, THEN it retrieves that data from its own system's state, not from the session record.

### Core Rule 9 — sessionId never leaks via logs/telemetry
- [ ] GIVEN any server log line, error report, or telemetry event is generated during normal operation, WHEN its contents are inspected, THEN it never includes a `sessionId` value — a `playerId` is used instead wherever a player reference is needed for debugging/analytics.

### States and Transitions
- [ ] GIVEN a brand-new Socket.IO connection with no `sessionId` exchanged yet, WHEN the connection's state is inspected, THEN it is `connecting`.
- [ ] GIVEN a client in `connecting`, WHEN `SESSION_ESTABLISHED` is sent and received, THEN the session transitions to `identified`.
- [ ] GIVEN a session in `identified` (no `displayName`/`playerId`/room), WHEN `JOIN_ROOM` succeeds, THEN the session transitions to `active_player`.
- [ ] GIVEN a session in `identified`, WHEN any message other than a successful `JOIN_ROOM` is processed, THEN the session remains in `identified` (no premature transition to `active_player`).
- [ ] GIVEN a session in `active_player`, WHEN the socket disconnects, THEN the session transitions to `disconnected` and the server retains the session record (not deleted immediately).
- [ ] GIVEN a session in `disconnected`, WHEN a client reconnects with the matching `sessionId` before eviction, THEN the session transitions back to `active_player` with `displayName`, `playerId`, and room membership intact.
- [ ] GIVEN a session in `disconnected`, WHEN the session record is evicted (per Reconnection & Session Identity policy) before any reconnect, THEN the session reaches a terminal state and a later reconnect attempt with that `sessionId` is treated as unrecognized (falls to Core Rule 4's fresh-issuance path).
- [ ] GIVEN a session in `disconnected`, WHEN other players' clients are observed, THEN that player is shown as disconnected (not removed) until eviction or reconnection resolves it.

### Formula — Session ID Collision Probability (no uniqueness check needed)
- [ ] GIVEN the server generates a new `sessionId` via `crypto.randomUUID()`, WHEN the generation logic is inspected, THEN it performs no lookup/comparison against existing session records before accepting the new ID (no uniqueness check is implemented, consistent with the formula's conclusion).
- [ ] GIVEN n = 10,000 concurrent sessions substituted into `P_collision ≈ (n^2) / (2 * 2^122)`, WHEN the result is computed, THEN it evaluates to approximately 9.4×10^-30, confirming the "safe to treat as zero" claim used to justify omitting a uniqueness check.
- [ ] GIVEN the realistic operating range of this game (2–12 players per room, small number of concurrent rooms), WHEN n is substituted at the upper generous ceiling (10^6) from the formula's stated range, THEN `P_collision` still evaluates to a value effectively indistinguishable from 0 (well under any reasonable risk threshold, e.g., < 10^-18).

### Edge Cases
- [ ] GIVEN `sessionStorage` is cleared, disabled, or unavailable (e.g., private browsing mode blocking it), WHEN the client attempts to read a stored `sessionId` and finds none, THEN the client proceeds with no `sessionId` in the handshake and the server issues a brand-new session with no error shown.
- [ ] GIVEN a client sends a `sessionId` the server has never issued or has already evicted (forged, tampered, or stale), WHEN the server processes the handshake, THEN it responds identically to the "no sessionId provided" case — a fresh session is issued, with no error and no signal distinguishing "forged" from "expired" from "never existed."
- [ ] GIVEN the same person opens two separate browser tabs to the game (no shared `sessionStorage` between tabs), WHEN both tabs connect, THEN each receives a distinct `sessionId` and both can independently become `active_player` sessions (even with the same `displayName`), and neither tab's actions affect the other's session state.
- [ ] GIVEN the server process restarts (all in-memory session records cleared), WHEN a previously-connected client's socket reconnects with its old `sessionId`, THEN the server does not recognize it, issues a fresh `sessionId` per Core Rule 4, and the client shows no error — any prior room/game state for that session is not restored (accepted tradeoff, not a bug).
- [ ] GIVEN a session already in `active_player` (has a `displayName` via a prior successful `JOIN_ROOM`), WHEN that session sends a second `JOIN_ROOM` call, THEN the identity layer imposes no rule of its own on the outcome — behavior is fully delegated to Room/Lobby, and this system's `sessionId`↔`displayName` pairing mechanism does not itself error, crash, or corrupt the existing pairing regardless of what Room/Lobby decides.
